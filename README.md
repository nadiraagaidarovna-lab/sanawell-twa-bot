# SanaWell — Telegram Web App бот (MVP)

Бот поддержки женщин в перименопаузе: анонимный трекер сна/настроения/когнитивного состояния
(3 кнопки), карточки самопомощи, экран прогресса «Мой путь», мягкие ежедневные напоминания
и выбор языка (казахский/русский). Реализован по ТЗ v2 (7-дневный спринт, Модули 1–5).

## Структура проекта

```
sanawell-twa-bot/
├── backend/
│   ├── src/
│   │   ├── server.js       — Express-сервер, раздаёт API и mini-app/dist
│   │   ├── routes.js       — /api/me, /api/language, /api/consent,
│   │   │                      /api/reminder-opt-in, /api/checkin, /api/protocols,
│   │   │                      /api/safety-check, /api/partners
│   │   ├── telegramAuth.js — проверка подлинности initData (HMAC по спецификации Telegram)
│   │   ├── db.js           — Postgres (Neon, free-тир), только telegram_id, без ПДн
│   │   ├── protocols.js    — контент микро-протоколов самопомощи (id + логика; перевод — во фронтенде)
│   │   ├── safety.js       — детектор маркеров риска (ru + kk одновременно) + телефоны доверия
│   │   └── bot.js          — /start + кнопка Web App + планировщик ежедневных напоминаний
├── mini-app/                — React + Vite + @telegram-apps/sdk, см. ниже.
│   ├── src/
│   │   ├── screens/         — HomeScreen, CheckinScreen
│   │   ├── components/      — ScaleSlider (шкала 1-10 с haptic feedback)
│   │   └── lib/              — telegram.ts (SDK/тема/mock), navigation.tsx, api.ts,
│   │                           useMainButton.ts, useBackButton.ts
│   └── dist/                 — сборка (не коммитится, собирается на каждом деплое)
├── render.yaml              — конфиг для Render
├── .node-version             — пин версии Node.js (см. package.json engines)
├── .env.example
└── package.json
```

## Модуль 4 — возврат и вовлечение

- **Пропуск онбординга.** `GET /api/me` при каждом открытии Web App сообщает фронтенду,
  проходил ли пользователь согласие раньше (по `telegram_id`).
- **Напоминания.** Чекбокс на онбординге (по умолчанию выключен) → `reminder_opt_in` в БД.
  `backend/src/bot.js` каждые 5 минут проверяет текущий час по Алматы и рассылает сообщение
  всем, кто ещё не получал его сегодня, с кнопками «Открыть» и «Отключить» — отключение
  работает в один клик через `callback_query`, без повторных предложений включить обратно.

## Модуль 5 — язык (казахский/русский)

- Выбор языка сохраняется и на сервере (`POST /api/language`), и в `localStorage` (на случай
  сетевого сбоя при следующем открытии).
- **Детектор риска в `safety.js` проверяет русские И казахские маркеры одновременно и всегда**,
  независимо от того, какой язык выбран в интерфейсе (ТЗ 5.4) — подтверждено тестом
  `backend/test/verify-auth.js`.
- **Важно:** казахский текст — черновой перевод для MVP-спринта. Перед запуском на реальных
  пользователях нужна вычитка носителем языка (в первую очередь — казахские паттерны в
  `backend/src/safety.js`, где цена ошибки перевода особенно высока).

## Mini App: ежедневный чек-ин (React + @telegram-apps/sdk)

Новый модуль по `TZ-v2.1.md` (Этап 1) — не переписывает старый трекер, а живёт рядом с ним
на отдельном пути `/checkin`. Полная история решений и найденных по пути нюансов — в git-логе
(6 последовательных срезов), здесь только суть:

- **Frontend:** `mini-app/` — отдельный React-проект (Vite + TypeScript), собирается отдельно
  (`npm --prefix mini-app run build`) и раздаётся тем же Express-сервером статикой на `/checkin`
  (см. `server.js`). `vite.config.ts` собирает с `base: '/checkin/'` — иначе ассеты ссылались бы
  на корень домена.
- **Тема и навигация** — через `@telegram-apps/sdk`: системная тема Telegram (`--tg-theme-*`),
  нативные `MainButton`/`BackButton`/`HapticFeedback` вместо кастомных кнопок (ТЗ 4.1).
- **Локальная разработка вне Telegram** — `mockTelegramEnv` из SDK, включается по
  `import.meta.env.DEV` (не по `isTMA()` — тот даёт ложный "да" после первой перезагрузки,
  потому что мок сохраняет launch params в `sessionStorage`). Для теста против настоящего
  бэкенда нужна по-настоящему подписанная initData — сгенерируйте её тем же алгоритмом, что и
  `backend/test/verify-auth.js`, реальным `BOT_TOKEN`, и положите в `mini-app/.env.local` как
  `VITE_MOCK_INIT_DATA` (файл в `.gitignore`, не коммитится).
- **Данные:** новая таблица `daily_checkins` — одна запись в день (Алматинские сутки), числовая
  шкала 1–10 по сну/настроению/памяти + свободный комментарий. Отдельная сущность от старого
  `logs` (там символьные коды по нажатию кнопки, здесь дневной агрегат) — намеренно не смешаны.
- **`GET /api/checkin`** — чек-ин за сегодня, если есть; **`POST /api/checkin`** — upsert по дню,
  `corrected_manually` выставляется автоматически при повторной отправке. Окно «Исправить»
  (24 часа от `created_at`) считается на бэкенде, не доверяется часам клиента.
- **Без LLM-обработки** (извлечение тем, safety_flag) — согласно `TZ-v2.1.md` раздел 16, это
  Этап 2, не Этап 1. `safety_flag` в схеме БД — заглушка `false`.
- Вторая кнопка в `/start`-сообщении бота («Ежедневный чек-ин») ведёт на `${WEBAPP_URL}/checkin`
  — первая кнопка (старый трекер) не убрана.

## Почему Postgres (Neon), а не SQLite

Изначально был `node:sqlite` на локальном файле — простое встроенное решение без нативной
сборки. Но у бесплатного тарифа Render нет постоянного диска: файловая система эфемерна,
и файл базы стирался на каждом деплое и на каждом выходе инстанса из сна (обнаружено
09.09.2026 — все данные пользователей, чек-ины, язык, согласия исчезали регулярно и незаметно).
Платный план Render с постоянным диском потребовал бы привязать карту к аккаунту — вместо
этого проект переехал на [Neon](https://neon.tech): managed Postgres с честным бесплатным
тиром без карты. Хранилище там отделено от компьюта — компьют может «засыпать» при простое,
это добавляет задержку на «разбудить» при следующем запросе, но не стирает данные (в отличие
от эфемерного диска Render). `DATABASE_URL` — переменная окружения (`.env` локально,
env var в Render, без диска и без карты).

## Известный остаточный пункт `npm audit`

`node-telegram-bot-api@0.66.x` тянет за собой устаревший пакет `request` с открытой
умеренной уязвимостью SSRF (`GHSA-p8p7-x288-28g6`). Мажорный апгрейд до
`node-telegram-bot-api@2.x` убрал бы её, но там полностью другой, несовместимый API (не
`onText`/`sendMessage`/`polling`, а конструкции в духе `Bot`/`Api`/`Context`) — переписывать
`bot.js` под непроверенную библиотеку в рамках MVP-спринта рискованнее, чем оставить
уязвимость. SSRF в `request` эксплуатируется только если сам код передаёт в HTTP-клиент
URL, полученный от пользователя — здесь `request` используется исключительно для обращения
к фиксированному `api.telegram.org`, куда пользовательский текст никогда не попадает как URL.
Остальные транзитивные уязвимости (`form-data`, `qs`, `tough-cookie`, `uuid`) закреплены на
пропатченных версиях через `overrides` в `package.json` — `npm audit` подтверждает 0 проблем
по ним. Стоит пересмотреть при следующей ревизии зависимостей.

## День 3: регистрация бота и локальный запуск

1. **Получить токен.** В Telegram напишите `@BotFather` → `/newbot` → укажите имя и username
   (например `sanawell_support_bot`). Скопируйте выданный токен.
2. Скопируйте `.env.example` в `.env` и вставьте токен в `BOT_TOKEN`.
3. Установите зависимости:
   ```bash
   npm install
   ```
4. **Web App нужен публичный HTTPS-адрес** — Telegram не откроет `localhost`. Для локальной
   отладки проще всего пробросить туннель, например через `ngrok`:
   ```bash
   ngrok http 3000
   ```
   Полученный `https://...ngrok-free.app` адрес впишите в `WEBAPP_URL` в `.env`.
5. Запустите сервер:
   ```bash
   npm start
   ```
   Сервер поднимется на `http://localhost:3000`, будет отдавать API и собранный mini-app, и в
   этом же процессе стартует бот (см. ниже, «Один процесс на бота и API») — отдельно его запускать не
   нужно, если `BOT_TOKEN`/`WEBAPP_URL` заданы в `.env`.
6. В Telegram отправьте боту `/start` — придёт приветствие и кнопка «Открыть».

### Один процесс на бота и API

`server.js` при старте вызывает `startBot()` из `bot.js` в том же процессе — оба используют
одну и ту же базу на Neon (`DATABASE_URL`). Это осознанный выбор для деплоя одним сервисом
(см. «Почему Postgres (Neon)» выше и раздел «День 7: деплой»): если бот и API работают в
разных процессах, планировщик напоминаний физически не увидит согласие/язык/подписку,
сохранённые через API. Отдельный запуск (`npm run bot`) по-прежнему доступен — например, для
локальной отладки бота без поднятия всего сервера, — `DATABASE_URL` в `.env` один и тот же
для обоих способов запуска, отдельно указывать ничего не нужно.

### Валидация initData

Проверка подлинности данных из Web App (файл `telegramAuth.js`) реализована строго по
[официальной спецификации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-web-app):
HMAC-SHA256 по отсортированным параметрам, секрет — HMAC от токена бота. Все API-роуты
защищены этой проверкой через заголовок `X-Telegram-Init-Data`.

## День 6: safety-check (маркеры риска)

`backend/src/safety.js` — простая проверка по ключевым фразам (суицидальные маркеры, тяжёлая
депрессия). Это **не клиническая оценка риска**, а базовый MVP-фильтр: при срабатывании бот
не показывает обычные протоколы самопомощи, а выводит номера телефонов доверия и рекомендацию
обратиться к специалисту очно.

**Важно перед запуском на реальных пользователях:**
- Список триггерных фраз в `RISK_PATTERNS` нужно проверить и расширить вместе с
  психологом/психиатром-партнёром — сейчас это стартовый набор для MVP, не полное покрытие.
- Актуализируйте номера телефонов доверия в `SAFETY_RESOURCES` (указаны общий номер 150 и
  экстренный 112 — проверьте актуальность и добавьте локальные ресурсы, если есть).
- Продукт по ТЗ строго не должен: ставить диагнозы, рекомендовать анализы, рекомендовать ГЗТ.
  Тексты в `protocols.js` и `bot.js` спроектированы с учётом этого — при добавлении нового
  контента держите эту границу.

## День 7: деплой

### Render
1. Запушьте репозиторий на GitHub (см. «Git и GitHub» ниже, если ещё не сделано).
2. На Render: **New → Blueprint** → укажите репозиторий (подхватит `render.yaml`; сервис
   один — `sanawell-twa-bot`, `type: web`, план `free`).
3. В настройках сервиса заполните переменные окружения `BOT_TOKEN` (токен от `@BotFather`),
   `DATABASE_URL` (connection string из Neon-проекта — Dashboard → Connect, вариант pooled
   connection) и `WEBAPP_URL` — **это URL самого сервиса на Render** (например,
   `https://sanawell-twa-bot.onrender.com`), поэтому сначала разверните сервис один раз, узнайте
   присвоенный адрес, впишите его в `WEBAPP_URL`, затем передеплойте (Manual Deploy).
4. Проверьте, что `render.yaml` использует именно `npm start` (сервер сам поднимет и API, и
   бота — см. «Один процесс на бота и API» выше). Отдельный background worker для бота **не
   нужен и не будет работать корректно**: два сервиса на Render не делят файловую систему, а
   значит планировщик напоминаний в отдельном воркере не увидел бы согласие/язык/подписку,
   сохранённые через API в БД веб-сервиса. По той же причине `mini-app` собирается на том же
   сервисе: `buildCommand` ставит зависимости и собирает React отдельным шагом
   (`npm install && npm --prefix mini-app install && npm --prefix mini-app run build`) —
   `mini-app/dist` не коммитится, собирается заново на каждом деплое.
5. **Известное ограничение бесплатного плана Render:** free-сервис засыпает после ~15 минут
   без входящих HTTP-запросов и просыпается только на следующий запрос — значит планировщик
   напоминаний (`setInterval` внутри процесса) тоже не сработает, пока сервис спит, и вечернее
   напоминание может не уйти вовремя. Для по-настоящему круглосуточной работы планировщика
   нужен платный план Render (без автозасыпания) — это стоит учитывать перед реальным запуском
   на пользователях, даже если для тестирования скелета free-плана достаточно.

### Amvera
Аналогично: Node.js-приложение, `npm start` как команда запуска, те же переменные окружения
(`BOT_TOKEN`, `WEBAPP_URL`, опционально `REMINDER_HOUR`). Уточните у хостинга, не засыпает ли
процесс при простое — по той же причине, что и на Render free-плане.
